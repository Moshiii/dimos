# Let control tasks pull cached coordinator state

The control coordinator retains the most recent complete tick observation and constructs one frozen, stateless `ControlTaskContext`, initially containing only `get_state()`, which it shares across registered `BaseControlTask` instances. The context owns function handles rather than observations, locks, threads, or hardware access; future helpers must be coordinator-owned operations generally needed by tasks and safe to invoke while the task lock is held. `TickLoop` constructs one structurally read-only `CoordinatorState` per tick, supplies it to one coordinator callback before active-task filtering, and then shares the same object with active tasks through `compute()`. The coordinator stores the observation under a dedicated state lock that is released before task computation. A task may pull the cached object by reference when handling a command outside `compute()`, but it does not depend on the complete coordinator or initiate hardware reads. `get_state()` returns `None` before the first observation and does not check freshness because a stalled control tick is a system failure outside this interface's responsibility. Stopping the tick loop or resetting runtime state clears the cached observation; registered tasks keep their contexts across restart and observe `None` until the next complete tick. Registration binds the context, removal detaches it, binding to a different coordinator while still registered is rejected, and context access while unbound fails as a lifecycle error. External structural `ControlTask` implementations remain compatible but receive no context implicitly. `JointTrajectoryTask.execute()` accepts only a trajectory, obtains its validation state through the bound context, and returns `START_STATE_UNAVAILABLE` when no tick observation exists; callers cannot inject an alternate position snapshot. Because trajectory execution is an optional task capability, `ControlCoordinator` has no trajectory-specific methods, imports, fields, cardinality rules, or result handling; callers use the generic declared task-command route. The trajectory-task package owns and enforces the canonical hardware-neutral task name `joint_trajectory`, so required coordinator task-name uniqueness admits at most one JTT and `ManipulationModule` needs no task-name configuration. `TASK_EXPOSES` is a strict remote-command allowlist: the coordinator rejects undeclared methods instead of reflectively invoking them, and invoking an unregistered task raises an error rather than returning `None`. Missing-task errors do not appear in trajectory result enums because those values describe semantic outcomes returned by an existing task. The generic coordinator returns declared command values unchanged; task-aware callers such as `PlanExecutionManager` own any projection into caller-layer outcomes.
